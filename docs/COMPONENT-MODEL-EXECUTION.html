How the pieces execute

Four figures, in execution order: who owns each type, what happens when the renderer meets a component, how one raw invocation becomes resolved bindings, and why a reactive change re-renders exactly one component.

Status — shipping component-model standard

This page describes the shipping standard delivered by the [V01.01.15] component-model arc. The types and execution paths shown here are implemented by the runtime libraries under libraries/.

Rationale, the assembly-seam analysis, and the completed migration record live in the COMPONENT-MODEL-PLAN.md plan of record. Normative semantics remain SPECIFICATION.md; clause ids are cited below where this design preserves or extends a specified behavior.

1 · Who owns what — one word, four lifetimes

[CMP-1] already separates three roles that one object would otherwise conflate: render description, authored behavior, and runtime bookkeeping. This design makes the fourth — the static identity and declaration — explicit too, and gives each an owner. Components holds three of them; only mounted bookkeeping lives in Core.

2 · First mount — the engine drives, the model is what it touches

Everything below happens synchronously inside one patch walk, with no reflection anywhere [EXE-4]: every step is a dictionary lookup, a delegate call, or a plain method. The renderer receives a per-mount ComponentRenderFrame — the render cache and block assembly ride the parameter, so there is no ambient helper state and no public static helper class.

The same nine steps, seen from the generated .viu component's side:

partial class Counter : ComponentBase, IComponent
{
    // ③ read before activation — the contract rides the registration
    static readonly ComponentContract __ViuContract = new(
        "Counter", ComponentFlags.InheritFallthroughBindings,
        parameters: [new ComponentParameter("count", isRequired: true), new ComponentParameter("title")],
        events:     [new ComponentEvent("increment")]);

    ComponentRenderer IComponent.Setup(ComponentContext context)   // ⑦
    {
        Context = context;
        var store = CounterStore.Definition.Use(context);            // seam: Services + ambient — no cast
        context.Watch(() => store.Total, (current, previous) => …); // scoped to this mount
        return frame => Render(this, frame);                          // ⑧ → VirtualNode subtree
    }
}

3 · One invocation, resolved — raw request vs. mounted view

The old duplication (Arguments/Slots/Attributes declared twice with the same names) dissolves because the raw request and the resolved view are now different types with different names, connected by one documented transform. Parameter binding still re-runs per render [CMP-29].

4 · The update — component-local invalidation, block-local patching

This is Viu's founding rendering objective, preserved: a state change re-runs only the render closures that read it, and the resulting diff visits only what the compiler marked dynamic. The three-state block contract of [RND-BLOCK-1] and the frozen patch-flag layout of [RND-FLAGS-1] carry over unchanged under the RenderPlan name.
